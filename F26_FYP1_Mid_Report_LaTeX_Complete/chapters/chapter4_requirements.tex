\chapter{Software Requirements}

\section{User Interactions / Use Cases}
The system operates with three main types of interaction of the user:
\begin{enumerate}
    \item \textbf{Capture}: The user starts the application on Android, initiates recording operation, then walks around the room being shown feedback on the recording quality, and stops recording after this and taps ``Upload \& Process.''
    \item \textbf{Monitor}: The user monitors the processing progress showing the current phase, percentage completed, time elapsed, and logs.
    \item \textbf{View/Measure}: The user checks the resultant 3D model on the web viewer and can calculate certain distances (FYP-2).
\end{enumerate}

\section{Use Case Diagram}
The implementation of the system consists of three actors (See Figure~\ref{fig:usecase}): \emph{End User} (perform captures and views), \emph{Processing Server} (executes jobs), and the \emph{Cloud GPU} (carries-out reconstruction). The use cases are Record Scan, Upload Dataset, Monitor Progress, View Model, Take Measurements and Configure Server. Each of them has the relevant code: Record Scan corresponds to \texttt{HelloArActivity} and \texttt{CaptureLogger}; Upload Dataset and Monitor Progress refer to \texttt{ProcessingActivity} and the \texttt{/upload} and \texttt{/status} endpoints of \texttt{server/main.py}; Configure Server links to the settings menu of the app (server URL) and \texttt{/config}; View Model and Take Measurements correspond to the desktop viewer today and web workspace in phase FYP-2.

\section{Detailed Use Cases}

\paragraph{UC-1: Record Indoor Scan}
\begin{itemize}
    \item \textbf{Actor}: User
    \item \textbf{Precondition}: Application downloaded on Android device compatible with ARCore.
    \item \textbf{Flow of Events}: The User starts the application $\rightarrow$ presses Record $\rightarrow$ moves around the space $\rightarrow$ gets live feedback regarding IQA (blurriness, speed, darkness, texture)$\rightarrow$ stops the recording $\rightarrow$ app displays the summary of quality data.
    \item \textbf{Postcondition}: The information is saved on the device (video, poses, depth, quality, meta).
\end{itemize}

\paragraph{UC-2: Upload and Process}
\begin{itemize}
    \item \textbf{Actor}: User
    \item \textbf{Precondition}: Recording is over; URL of the server is configured.
    \item \textbf{Flow of events}: The User clicks on Upload and Process $\rightarrow$ the app compresses the files and uploads them onto the server $\rightarrow$ server creates a job and sends it to GPU $\rightarrow$ app checks progress every 3 seconds communicating step, percentage, logs.
    \item \textbf{Postcondition}: The 3D model (\texttt{splat.ply}) is ready for downloading.
    \item \textbf{Exception}: The upload does not go through $\rightarrow$ button for retrying exists; failure of the process $\rightarrow$ error message shows the step name.
\end{itemize}

\section{Acceptance Criteria}
\label{sec:acceptance}
All acceptance criteria are specified in Tables~\ref{tab:fr} and \ref{tab:nfr}. Project's acceptance limits are set as: held-out PSNR $\geq$ 25\,dB and SSIM $\geq$ 0.85 (FR-P4; achieved by version 6), difference no more than 5\% vs actual measure (FR-P3; achieved with the greatest difference of 0.29\%), and processing duration should not exceed 35\,min on RTX 4090 (NFR-P1; not measured yet).
